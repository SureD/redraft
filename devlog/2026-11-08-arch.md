# 技术选型与开发路线

- **缘由**　搭骨架之前，先确定平台、文档格式、编辑器、diff 方案和存储方式，并排好开发顺序。后续每一步都建立在这些决定之上，所以要写清理由，方便日后回看，也方便在条件变化时推翻重来。
- **改动**　本次只做选型，不建工程，不写代码。下面列出八项决定和一条开发路线。
- **验证**　由作者审阅本日志，确认或修改每项决定。依赖第三方库能力的假设，放到路线第 1 步用小样验证，结论再写回这里。

## 选型

### 1. 客户端平台：Swift 原生，先做 macOS

- **候选**　Tauri、Electron、Swift 原生（SwiftUI 搭界面，正文编辑用 AppKit）。
- **选择理由**　目标是 Notes 那样的原生写作体验。原生应用直接获得系统输入法（包括中文组字）、拼写检查、Writing Tools、辅助功能和服务菜单，内存占用低，启动快。
- **代价**　用不上 Web 编辑器的成熟生态；跨平台只能覆盖 Apple 系平台。
- **路线**　先做 macOS。核心逻辑写成不依赖 UI 的 Swift Package，以后接 iPadOS 和 iOS 时复用。

### 2. 文档真相源：Loro CRDT，Markdown 只做导出

- **候选**　Markdown 文件、ProseMirror JSON 加版本快照、Automerge、Yjs、Loro。
- **选择理由**　产品要求从定稿回看一句话的来历，这需要每段文字都有稳定的身份。Markdown 只是字符序列，编辑以后偏移量会变，批注锚点容易漂移。Loro 给每个字符分配唯一身份，用 `Cursor` 做锚点，增删文字也不会漂移。它自带完整的操作历史，可以回到任意版本（`checkout`、`forkAt`），原生支持富文本 mark，快照紧凑。以后如果要做多设备同步，也不用改数据模型。
- **为什么不选其他 CRDT**　Yjs 没有官方 Swift 绑定。Automerge 的 Swift 绑定更成熟，作为备选。
- **风险**　loro-swift 官方标注为 experimental。富文本 mark、`Cursor`、`forkAt` 在 Swift 侧是否都可用，需要实测。所有 Loro 调用收在同一层，万一要换成 Automerge，影响范围可控。

### 3. 编辑器：TextKit 2（`NSTextView`）

- **候选**　SwiftUI `TextEditor` 加 `AttributedString`、TextKit 2 的 `NSTextView`、在 `WKWebView` 里嵌 ProseMirror、STTextView（GPL 和商业双许可）。
- **选择理由**　Notes 本身基于 TextKit，用它最接近原生体验。输入法、拼写检查、Writing Tools 都是现成的。批注高亮可以用 rendering attributes 叠加绘制，不改动正文内容；修订样式可以用自定义的 layout fragment 绘制。SwiftUI `TextEditor` 代码最少，但对渲染和选区的控制不够，做不好批注和修订。
- **代价**　`NSTextStorage` 和 Loro 之间的同步层要自己写。
- **风险**　输入法组字期间不能把半成品同步进 Loro，要等确认上屏以后再同步。`NSString` 按 UTF-16 计数，Loro 默认按 Unicode 字符计数，同步层要统一转换。

### 4. AI 批注协议：结构化的建议条目

- **候选**　让 AI 返回整篇改写稿，再用 diff 找出改动；或者让 AI 直接返回一组建议条目。
- **选择**　每条建议的格式是 `{ quote, prefix, suffix, issue, reason, replacement }`，即原文引用及其前后文、问题、理由和建议改法。锚点格式参考 W3C Web Annotation 的 TextQuoteSelector：先精确匹配原文，失败再模糊匹配，定位后转换成 Loro `Cursor`。
- **选择理由**　修改意图和理由能原样保留，每条建议可以单独采纳、拒绝或自己重写。整篇改写稿做 diff 会产生大量噪音，也会丢掉"为什么这样改"。
- **兜底**　作者要求整篇重写时，才退回到 diff。

### 5. Diff 算法：分层 diff

- **候选**　只做字符级 diff（如 diff-match-patch），行级的 patience 或 histogram diff，分层 diff。
- **选择**　分三层处理：
  1. 段落层：按段对齐，配合相似度阈值识别改写过的段落。
  2. 句和词层：用 `NaturalLanguage` 框架的 `NLTokenizer` 切句、切词（原生支持中文分词），再用 Swift 标准库的 `difference(from:)` 比较词元序列，它的实现就是 Myers 算法。
  3. 语义清理：参考 diff-match-patch 的 `cleanupSemantic`，把两处修改之间零碎的相同片段合并掉。
- **选择理由**　对写作来说，切分粒度比算法本身更影响结果的可读性。字符级 diff 在中文里会把一个词拆得七零八落；行级 diff 对没有换行的长段落几乎无效。整套方案只用系统框架，不引入依赖。
- **适用场景**　版本对比（用 `forkAt` 取出两个版本的正文后比较）、整篇重写、导入外部稿件。如果以后 Swift 绑定暴露了 Loro 的精确变更接口，版本对比可以改用它，对外接口不变。

### 6. 本地存储：每篇文章一个目录

- **候选**　SQLite、document-based app（每篇文章是一个独立文件，由用户自行保存）、应用管理的文章库目录。
- **选择**　文章存放在 `~/Library/Application Support/Redraft/Library/<uuid>/`，目录里放 `doc.loro`（快照）和 `export.md`。
- **选择理由**　与 Notes 式的文章库形态一致，用户不用管文件放在哪。Loro 快照已经包含全部历史和批注，不需要另建数据库。附带的 Markdown 导出让用户随时能直接查看和备份。

### 7. 工程组织：XcodeGen 加本地 Swift Package

- **候选**　手工维护 `.xcodeproj`、Tuist、XcodeGen。
- **选择理由**　XcodeGen 用一份可读的 `project.yml` 生成工程。评审时能直接看 diff，没有 `.xcodeproj` 的合并冲突，agent 也能直接修改。核心包可以单独运行 `swift test`，不用启动 App。
- **代价**　需要先安装 XcodeGen（`brew install xcodegen`）。

### 8. AI 服务：先定协议，配一个 Mock 实现

- **选择理由**　批注流程（请求、定位、高亮、采纳）与具体用哪家模型无关。先用 Mock 跑通整条流程，接入真实模型时只替换实现。
- **待定**　模型服务商的选择和 API key 的保存方式（倾向 Keychain），留到路线第 9 步决定。

## 开发路线

每一步都按 [开发流程](../devflow.md) 走一遍：先写设计，再实现，最后写 devlog。

1. **关键假设验证**　写一次性小样，确认 loro-swift 的 mark、`Cursor`、`forkAt` 可用，在 TextKit 2 里用中文输入法输入时与 Loro 同步正确，UTF-16 下标转换正确。失败就启用备选方案，并修改本日志。
2. **架构设计文档**　写清模块划分和数据协议，用一条完整的写作流程把模块串起来。
3. **工程骨架**　空的 App 能启动，核心包的测试能跑通。
4. **文档模型与本地存储**　关闭文章后重新打开，草稿能恢复。
5. **编辑器与同步**　中英文输入和粗体、标题等格式都能正确写进 Loro。
6. **Diff 引擎**　中英文样例的分层 diff 结果符合预期。
7. **AI 批注闭环**　用 Mock 服务跑通批改、高亮、批注卡片、采纳或拒绝。
8. **版本历史与溯源**　能标记版本、对比任意两个版本、查看一句话的演变。
9. **接入真实 AI**　选定模型服务，管理 key，完成提示词和输出校验。

第 1 步排在架构文档之前，是因为 loro-swift 的成熟度和中文输入法同步是整套方案里最没把握的两点。先确认它们可行，再在上面做设计。
